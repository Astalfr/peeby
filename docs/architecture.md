# Architecture

```
┌──────────────────────────────────────────────────────────────────────────┐
│ peeby (GPUI app)                                                         │
│  shell: top bar (tabs, +, search, bell, gear) · sidebar · mini-player   │
│    │                                                                     │
│    ├── spaces::youtube ── innertube ──────► www.youtube.com (InnerTube)  │
│    ├── spaces::jellyfin ─ jellyfin-api ───► the user's Jellyfin server   │
│    │        │                                                            │
│    ▼        ▼                                                            │
│  ui: theme, cards, images, rows, form, player ── player (libmpv) ──►     │
│                                                  gpui-video element      │
└──────────────────────────────────────────────────────────────────────────┘
   streams: *.googlevideo.com (HLS) · the Jellyfin server (Direct Play files)
```

## Threads and data flow

- **UI thread (GPUI).** Rendering and input only.
- **Network.** `reqwest` needs tokio, GPUI has its own executor. `ui::runtime` owns a 2-thread tokio runtime as a GPUI global; `runtime::spawn(cx, future)` returns a future that GPUI tasks await.
- **Player.** `ui::player::PlayerView` plays a `Source` and talks to its page through `PlayerEvent`s (`Started`, `Paused`, `Seeked`, `TracksChanged`, `Ended`, `Next`, `Previous`, `Close`, `Sound`, `Theater`); `Layout::Embedded` for YouTube's watch page, `Layout::Page` for Jellyfin's player, which is a page of its own in the content panel (back, title, Escape closes it), `Layout::Window` for a full-window player (the example). Chapters come from the file, or from the page (`set_chapters`: YouTube's, read from the `next` response); skippable segments come from the page (`set_segments`) or from the file's chapter titles; the "up next" card from `set_up_next`. The seek bar shows the loaded part ahead of the playhead (`Event::Cached`). The speed button (next to the quality, not on a live) picks 0.5× to 2×, kept across mpv restarts; Space or the left button held on the picture plays at 2× until the release (shown on top), a shorter press plays or pauses. A right click opens a menu with the shortcut help and a statistics panel (`stats.rs`), which reads a fixed list of mpv properties once a second while open, never `path` or `stream-open-filename` (stream URLs carry the user's IP). On a live it adds the delay to the streamer: the age of the playlist's end on the broadcaster's clock (`Source::live_edge`, from the space's proxy: Twitch's `PROGRAM-DATE-TIME`, `twitch::EdgeClock`; YouTube's `LiveProxy::edge_time`, when the edge segment appeared, so short of the real delay by YouTube's ingest) plus how far the playhead is behind that end (a DVR live's duration minus its position, else mpv's `demuxer-cache-duration`); on a recorded live's recording, how far behind now it plays. `Player::start` runs on GPUI's background executor (libmpv and D3D11 setup block briefly). mpv events and frames come back through channels (peeby's design).

## Twitch playback

The Twitch space's playback path:
1. `twitch::Client::play` asks GQL for two playback tokens together: `embed` for the main stream, which
   did not get the pre-roll, and `popout` as a backup without ads. It then gets both usher masters, with
   `supported_codecs` AV1, HEVC (the 1440p source of some channels) and H.264, less the codecs this PC
   decodes on the CPU (`[twitch] software_codecs`, learnt from mpv's `hwdec-current` by the watch page).
2. It starts a `Proxy` on `127.0.0.1`, on the network runtime.
3. mpv plays a variant's local URL, `/<random key>/<n>.m3u8`. On each reload the proxy fetches the
   variant's media playlist from Twitch and drops the ad segments. During an ad break it also fetches
   the backup playlist, and fills the break with its segments, lined up on Twitch's live sequence. With
   low latency (on by default), Twitch's prefetch segments follow the content, outside ad breaks.
4. Segments come from the CDN directly. Signed URLs and tokens stay in the proxy's memory.
5. Dropping the `Proxy` stops it.

## Startup

1. `peeby --login <service>` runs the sign-in window only and exits, before anything below (ADR 0017).
1. Before the UI starts: `settings::load_cookies()` reads and decrypts `%APPDATA%\peeby\cookies.dat` (or `PEEBY_COOKIES`; DPAPI, [ADR 0022](decisions/0022-encrypted-cookie-jar.md)), and `jellyfin::session::restore` reads the Jellyfin token from the Credential Manager (both blocking, both small).
2. In the background: `Client::refresh_client_version()` reads the current WEB `clientVersion` and a `visitorData` from the page's ytcfg; yt-dlp updates itself.
3. YouTube's Home loads `FEwhat_to_watch` (its response also carries a `visitorData`, kept for the stream resolver); Jellyfin's Home loads if a session was restored, else its tab shows the login page.

## Watch page

The stream (`Client::stream`, ~0.2 s), the page metadata (`Client::watch`) and the RYD votes load in parallel; the first comments page follows the metadata. RYD votes are cached for the session (100 requests/min, 10,000/day). mpv starts as soon as the stream is known: video media playlist as the file, audio rendition as `audio-files` (on a dubbed video, the original track: `acont=original` in its URI's `xtags`; the dubs come first in the group and none is `DEFAULT`), the VISIONOS User-Agent as an HTTP header. Measured: playback about 1.5 s after the page opens, player setup included.

`ui::player::PlayerView` owns the player, the `VideoView` and the controls, plus the source's quality ladder and subtitle tracks. It knows no service: the watch page turns the resolved stream into a `Source` (`convert::source`: one `Quality` per HLS variant with its own mpv options, the captions as `Subtitle`s, the storyboard as `Previews`), gives it the shared player settings and the caption language as `Prefs` (`settings::Player::prefs`), and saves what the player reports (`PlayerEvent::Sound`, `PlayerEvent::Theater`). A quality change starts a new mpv on the other variant at the current position (the old one is paused, then dropped when the new picture arrives). Subtitle tracks are given to mpv with `sub-add` the first time they are picked; mpv numbers them 1, 2… in that order.

`prefetch` resolves the stream of a card the mouse rests on (300 ms), and the watch page takes it from there. `prefetch::warm` resolves a stream at once (the next video of a queue). In fullscreen, the shell and `WatchView` render the player alone. A watch page covered by another page pauses its player (`set_covered`). Theater mode is a setting (`Settings::theater`), so the next videos of a queue keep it: the player toggles it and emits `PlayerEvent::Theater`, and the watch page lays itself out again, sizing the player from the window and the sidebar width.

## Navigation

`shell::Shell` is the window's root. It owns the top bar (menu button folding the sidebar, back and forward, logo, the open tabs and "+", search, the audio output menu, notifications, settings), the sidebar, filled with the entries of the shown tab's space, and the content panel, which renders that space's entity (or the settings page, opened by the gear as an entry of the tab's history, [ADR 0019](decisions/0019-tab-history.md)). **Tabs** ([ADR 0015](decisions/0015-tabs.md)): there is one entity per space (its session, sidebar data, bell and settings), and it holds a history of pages per tab of that space (`shell::space::Tabs`: back, forward, a page built when it shows); the shell keeps the tabs' order (`TabRef`: the space's index and a `TabId`) and tells the space which tab to render (`Space::show_tab`). "+" opens a tab of any space on its first page (`Space::new_tab`); "×" or a middle click on a tab closes it (`Space::close_tab`), never the last one. A tab held and moved past 4 px is reordered along the bar (`shell::tab_drag`, [ADR 0028](decisions/0028-tab-windows.md)): its canvas measures each tab at layout (`TabLayout`), window listeners registered at each paint while the button is held follow the pointer (not GPUI's `on_drag`, which stops at the window's edge), and the tab moves after the neighbors whose middle the dragged copy passed. Pages navigate through a `Nav` (their space and their tab), so what they open lands in their own tab. A middle click on a link (`MediaCard::on_middle_click`, `shell::space::middle_click`) or a sidebar entry opens it in a new tab after the current one, in the background: the space adds a tab whose page is not built (so nothing plays) and emits `SpaceEvent::Opened`; the page is built at the tab's first render. A tab is labeled by its page: the route's name, or the title a page sets once loaded (`Nav::set_title`: a video's, a VOD's, a Jellyfin title's). The settings page (`shell::settings_page`) holds the app's sections (general, the player's shared `[player]` settings, storage, about) and each space's part (`Space::settings`), the open space's first, each foldable and drawn in its space's accent (`theme::with_accent` while it is built, `theme::tinted` while it lays out and paints, since gpui-component's widgets read the theme then); a space asks for it with `SpaceEvent::OpenSettings` (YouTube's "Se connecter" buttons, Twitch's and Jellyfin's account entry); with `reveal`, the page unfolds that space's part and scrolls to it (`SettingsView::reveal`; the page's blocks are the scrolled element's own children for that), and the space may flash its account section (`ui::widgets::Flash`: two pulses of the accent, keyed by a generation so each request plays once, none with reduced motion). It knows the spaces only through the `shell::space::Space` trait: name, badge and accent, sidebar entries and opening one, its history (back, forward, the settings entry), the player of the page shown, unread notifications and the space's section of the notifications panel, and a `SpaceEvent::Activate(tab)` to be shown (a notification clicked from another tab: it opens in the space's last shown tab, or a new one). Adding a service means implementing `Space` and adding it to the list in `main.rs`. Switching tabs re-applies the space's accent (`theme::set_accent`) and does not pause anything.

Each tab keeps its own history ([ADR 0019](decisions/0019-tab-history.md)): opening a page drops the entries after the one shown and adds it, "back" drops the page left (its player stops), "forward" builds it again, and the 10 pages behind the one shown keep their view. `spaces::youtube::YouTubeSpace` (formerly `AppView`) renders the page shown in its shown tab with the page fade; the sidebar lights the last sidebar page or search up to it (Watch later is the `Playlist` route of `WL`, made top-level; History is a `FeedView` of `FEhistory`, always as a list), and those pages drop the watch and Shorts players behind them; a covered watch page pauses its player. `spaces::jellyfin::JellyfinSpace` shows its login page while signed out, then Home, the libraries, a title's page, the search, and the player; its settings are its part of the gear's page. The top bar's search button opens the open space's search page (`Space::searchable`, `Space::open_search`; YouTube's and Jellyfin's). In Jellyfin, any page opened drops a player behind it (it reports the playback stopped), the next episode replaces the player. A 401 from any page (`jellyfin::report`) signs the space out and its login page says the session expired. `peeby <url-or-id>` opens a video at startup.

**Jellyfin session** ([ADR 0009](decisions/0009-jellyfin-12-single-account.md)): `session::restore` reads the token from the Windows Credential Manager (service `peeby`, account `<server URL>|<user id>`, as in the former peeby) before the UI starts, with the server and user from `[jellyfin]` in the settings; signing in saves them (the token in the background), signing out deletes the token and the user and keeps the server. `[jellyfin].device_id` is made once. Jellyfin images and trickplay tiles need the session's `Authorization` header: `session::route_images` adds a `Fetch` for the server's URLs to the image store (`ui::images::route`) on sign-in and removes it on sign-out; the token is never put in a URL.

**Jellyfin playback**: `play::PlayView` negotiates Direct Play (anything else is refused with the server's reasons), downloads the fonts of external ASS subtitles to `%LOCALAPPDATA%\peeby\fonts\<item>`, gives the player a `Source` (the stream with the `Authorization` header, external subtitles, track names in mpv's order, trickplay as `Previews`), then the server's media segments and the previous and next episodes when they arrive. It reports Playing on start, Progress every 10 s and on pause, seek and track change, and Stopped once, also when the page is dropped (back, the sidebar, signing out, the next episode), marking the item played at the end; the page underneath then reloads. Track choices go from one episode of a series to the next for the session (`tracks::TrackMap`).

**Mini-player** ([ADR 0008](decisions/0008-mini-player-window.md)): leaving a page whose video plays (another tab, the settings) opens `shell::mini_player`, a `WindowKind::PopUp` window above every other one, at the bottom right of the main window's screen, drawing the same `VideoView`. It asks its space for the current player of its tab at each render (a queue carries on), closes when the page shows again or its tab is closed (its tab, or its own "Revenir à la page" button) and pauses then closes on "×". `ui::player::NowPlaying` keeps one sound at a time. Each window has its own.

**Windows** ([ADR 0028](decisions/0028-tab-windows.md)): every window is a `Shell` over the same spaces, holding some of their tabs; `shell::windows` keeps them (the window used last, set on activation, takes the notification area's icon, launches, toasts and the spaces' requests without a tab) and routes the spaces' events once for the app (`route_events`: to the window holding the tab concerned, else the one used last). A space renders in each window the tab that window shows (`Tabs::shown_in`). A tab dragged off the bar (`shell::tab_drag`) tears out into a window that follows the pointer and slides into the bar of a window it is carried over, still held (the window holding the tab drives the drag, the mouse's capture handed to it with `SetCapture`) (`windows::bar_at`, from each shell's bar layout and window position); its right-click menu also moves it to a new window. Its pages and video go with it. A window closed while another is open closes its tabs and stays hidden as a spare, reused by the next new window: the pages of a moved tab keep subscriptions bound to the window they were built in. The last one hides in the notification area or quits, as the single window did; the app quits when any of them really closes.

## Feeds

`FeedView` shows its videos through GPUI's virtual `list`: one item per row of cards (cards per row from the window width less the sidebar and the margins) or per list row, then an end item. Only the items in view, and those in the 800 px overdraw whose height is not known yet, are built on a frame. A plain scrolling div built every card on each wheel event, since GPUI re-renders the scrolled view. The end item coming into the list's reach loads the next page; new videos splice the last row and the new ones in. A change of layout or of cards per row rebuilds the items, keeping the first video in view.

## Playlists

`Client::playlists` reads the library (`FEplaylist_aggregation`, all playlists in one response, "Watch later" and "Liked videos" included), `Client::playlist` a playlist's page (`VL<id>`, header and the first 100 videos) and `Client::playlist_more` the next 100. "Watch later" lists `playlistVideoRenderer`s, the others video lockups; the next page's token is the `continuationItemViewModel` of the list holding the videos (the page has another one beside it).

Playing a playlist creates a `queue::Queue` entity: the loaded videos, the play order (shuffled or not), repeat, and the token of the next videos, which it loads when fewer than 5 are left to play. `YouTubeSpace::play_queue` pushes a watch page for its current video. That page shows the queue, subscribes to its player (`PlayerEvent::Ended`, `Next`, `Previous`) and to the queue (`QueueEvent::Play`). When the video ends, the queue picks the next one and `play_queue(…, replace: true)` swaps the watch page on top for a new one sharing the queue. Replacing rather than pushing keeps a single player alive for a whole playlist, drops the previous page's pending requests with it, and keeps "back" leading to the playlist. The new page takes the focus, so fullscreen and its keys carry on. Each page warms the next video's stream (`prefetch::warm`), so the next video starts in about 1.3 s.

Saving a video: `Client::playlist_choices` (`playlist/get_add_to_playlist`) lists the playlists and whether each holds the video; `Client::add_to_playlist` and `Client::remove_from_playlist` post `browse/edit_playlist` with the action that dialog's own endpoints carry (`ACTION_ADD_VIDEO`, `ACTION_REMOVE_VIDEO_BY_VIDEO_ID`). No `edit_playlist` response is saved yet: an HTTP success counts as done unless a `status` other than `STATUS_SUCCEEDED` comes back. `save::Session` (a global set by `YouTubeSpace`) gives the cards the current client; every change ends with a gpui-component notification (toast, bottom right) in the window it started from. `save::load_watch_later` reads the ids of the videos in "Watch later" at startup and on every session change (up to 50 pages of 100), and every successful change to that playlist updates them, so the thumbnails' shortcut shows a check on saved videos. Changes in flight are kept in a `Pending` set: their buttons show a spinner, and the same change is not sent twice.

Removing from a playlist: entries of a playlist the user can edit carry a `setVideoId` in an `ACTION_REMOVE_VIDEO` of their menu (`VideoItem::set_video_id`; "Watch later" and the user's own playlists, which list `playlistVideoRenderer`s). `Client::remove_playlist_entry` posts that action, so a video in a playlist twice loses only that entry. On success `save::edits` emits `EntryRemoved`; the playlist page and every queue of that playlist drop the entry. Removing the video a queue is playing leaves it playing, out of the queue (no row highlighted any more): Next, or its end, plays the video that followed it, and that video's stream is resolved ahead.

Shuffling uses a small xorshift generator (no dependency) and mixes the videos loaded so far: a long playlist's next pages are inserted at random places after the current video as they arrive.

## Channel notifications

The subscriptions feed (`FEsubscriptions`) mixes shelves (`richSectionRenderer`) into its grid: "Les plus pertinentes" first, then Shorts. `parse_subscriptions` (`Client::subscriptions`, `Client::subscriptions_more`) leaves them out and keeps the grid's own items: the lives on air, then the videos newest first. The shelf's videos are repeated further down, and since feeds drop repeated videos, keeping the shelf moved them to the top, out of date order.

A subscribed channel's subscribe button carries a `subscriptionNotificationToggleButtonRenderer`: the current level is the icon of the state `currentStateId` names, and the menu's items calling `modifyChannelNotificationPreferenceEndpoint` are the levels offered, each with its `params` (some channels offer only "Personnalisées" and "Aucune"). Not subscribed, YouTube still sends a bell, for after a subscription: the watch page parses it anyway (`WatchPage::notifications`) and shows it while subscribed, so it appears after a subscription made in Peeby; `FEchannels` and search results (`Channel::notifications`) keep it only when `subscribed` is true. The same button gives the subscription (`WatchPage::subscription`): `subscribed`, its `subscribeEndpoint`'s `params` and its `unsubscribeEndpoint`'s, inside the confirmation dialog. `subscribe::subscribe_button` posts them to `subscription/subscribe` or `subscription/unsubscribe` (`Client::set_subscribed`), with the same global by channel id, pending set and revert as the bell. The answer's `updateSubscribeButtonAction` must show the state asked for (`parse_subscribed`, fixtures `subscription_subscribe.json`, `subscription_unsubscribe.json`). A watch page read right after an unsubscription can still say subscribed for a while, so the session's global wins over the pages until the next session change.

`bell::bell_button` shows it. `Client::set_channel_notifications` posts the chosen option's `params` as they are (they embed the page's context, so each page keeps its own); the level set is kept by channel id in a global, so the watch page and the channels page agree, and it is forgotten on a session change. A change shows at once, blocks a second one for that channel while it runs, and goes back with a toast if YouTube refuses. No response of `modify_channel_preference` is saved yet: an HTTP success counts as done.

## Notifications inbox

youtube.com reads its inbox with `browse` (`FEnotifications_inbox`): sections (`multiPageMenuNotificationSectionRenderer`, "Important" then "Autres notifications") of `notificationRenderer`s, and a `continuationItemRenderer` whose next page (`browse` continuation) appends untitled items to the last section. The older `notification/get_notification_menu`, which yt-dlp still uses, now answers the empty-inbox promo even when the inbox is full (checked 2026-11-01, whatever the language, headers or context). `Client::notifications` and `notifications_more` parse it (`parse_notifications`); a notification opens its video (`watchEndpoint`, or `reelWatchEndpoint` for a Short).

`inbox::panel` is YouTube's section of the shell's notifications panel and `inbox::unseen` its part of the bell's badge, signed in only. `inbox::reset` (startup and every session change) reads `notification/get_unseen_count`, then again every 3 minutes; a session counter stops the reads of an old session. The badge starts at YouTube's count; when the count grows, the inbox's first page is read, and the notifications newer than the session (their id is their time in microseconds) not counted yet are added to the badge and shown as Windows notifications for the kinds that ask for it ([ADR 0020](decisions/0020-notifications-and-background.md)). Reading the inbox clears youtube.com's count a few seconds later (checked 2026-11-03), so it is read only then. A notification's kind (`NotificationKind`: upload, live, other) is the label in the bytes of its `clickTrackingParams` (`ni-push-u-sub`, `ni-push-lbss`). The red badge shows the count (9+ above nine). The panel lives in the popover's element state, so it loads the first page each time it opens, and the next page when its end comes within about a screen. It merges YouTube's sections into one list, newest first (by id), each next page included, and leaves out the kinds the settings keep out of the bell. Opening it sets the badge to 0 and marks read on YouTube the unread notifications of each page it loads: their `recordNotificationInteractionsEndpoint` tokens are posted to `notification/record_interactions` one after the other, as clicks on youtube.com (it has no request for several; no response saved yet, a failure is only logged). Their dot stays until the panel closes, to tell what was new. A click opens the video.


## Session

`YouTubeSpace::set_session` replaces the space's `Client` after a sign-in (the WebView window, ADR 0017, or a cookie import) or a sign-out and rebuilds the start page (`start_page`: Home or the subscriptions, the "Page d'accueil" setting; also the page shown at startup). The image store and the stream prefetch use an anonymous client of their own, so they never need replacing. Pages that need a session (Home signed out, subscriptions, an expired session) offer a "Se connecter" button (`YouTubeSpace::sign_in`) that opens the settings page on YouTube's part, whose account section (the sign-in window, the cookie import as the manual way) flashes. Twitch's "Se connecter" sidebar entry does the same for its account. Jellyfin's session is described under Navigation.

## Images

`ui::images::ImageStore`: GPUI global entity, in-memory LRU of decoded images (256 MB, every frame of an animated GIF or WebP counted; an `img` with an id plays them), disk cache in `%LOCALAPPDATA%\peeby\images`, 8 parallel downloads, `get_sized` for images decoded to an exact size, cache size and clearing for the settings. It downloads through a `ui::images::Fetch` the app gives it (`youtube::ImageFetch`, an anonymous InnerTube client), and through another one for the URLs of a route (`images::route`: the signed-in Jellyfin server), so it knows no service. BlurHashes are decoded to small images and cached (`ImageStore::blurhash`). Components take a `ui::picture::Picture`: fixed sizes to pick from (YouTube) or a URL for any size (servers that resize). The thumbnail size is picked from YouTube's `sources` for the card's physical width.
